# Keenetic / Netcraze installer automation (2.1.0-rc.1)

Status: candidate target **2.1.0-rc.1**, with publication authorized after software review and checks; **not hardware accepted**. Confirm the complete signed immutable RC release exists before installation. Published v2.0.1 assets remain unchanged. The maintained installation procedure is [AGENT_INSTALL.md](AGENT_INSTALL.md).

## Supported workflow

Entware is installed and mounted manually. The signed interactive bootstrap checks its release signatures/digests before running the dependency planner or wizard. Compatible existing native configurations retain read-only route discovery and mandatory native validation; only a unique unconditional VPN owner is adopted automatically. Ambiguous routes require a choice. Broken existing installations, competing services/hooks/processes or native cron entries require explicit operator reconciliation; missing executables are not published into an unknown existing service.

A clean installation offers the pinned XKeen 2.1 and Xray v26.10.21 payloads for the native MIPS BE/LE, ARMv7 or ARM64 ABI. Approval precedes any dependency publication. Exact archive size/SHA-256, safe extraction and native ELF checks remain mandatory. Entware packages, firmware, disk layout, SSH, DNS and WAN policies are not installed or modified. Required tools (`curl`, trusted CA/OpenSSL, `tar`, `unzip`, `jq`, `flock`, `timeout`, native `ip`/iptables/ipset/conntrack and process utilities, and compatible no-target-directory `ln`/`mv`) must already be available from the trusted Entware environment.

The RU/EN wizard keeps subscription URLs/headers and score/health URLs operator-supplied. In clean mode it stages strict JSON with loopback-only TCP/UDP transparent inbounds, a `bootstrap-blocked` blackhole outbound and explicit owned routing tags. Initial traffic is blocked until a successful explicit/runtime benchmark selects a working VPN. Defaults use pool/batch/latency/finalists=2, speed off and bounded subscriptions; this is a conservative starting point, not a qualified resource limit. Existing/prepared configuration defaults are preserved. Clean native interception is IPv4-only: existing IPv6 remains operator-owned, with no IPv6 leak-protection claim and no kernel IPv6 disable.

Native configuration is validated by the pinned executable with a bounded offline `run -test` before publication. The exact pinned XKeen service template is retained privately with maintained downstream changes: autostart is delegated to the signed wrapper, DSCP and `xkeen_full` interception are disabled, and missing/invalid policy marks refuse activation rather than using the upstream cached-mark or proxy-all fallback. No upstream `xkeen -i`, mutable installer or package self-heal runs.

Activation requires an existing, unique native `xkeen` policy with a nonzero valid mark and read-authorized loopback RCI. The operator creates/selects this policy in the router UI; KRM does not create it or reassign clients/WAN policy. Firmware requiring authorization needs a private token-only `KRM_XKEEN_CONFIG_FILE` (`{"rci_token":"..."}`), never a token in command arguments or logs. The native service remains inactive if the policy/token is unavailable or activation is declined. A distinct confirmation durably records permission to start interception for that policy, including guarded reboot startup. Committed native retries verify sibling links, ownership metadata and immutable payload identity before reusing consent or wizard presets. Only the explicitly private token JSON/activation receipt can differ from the inactive baseline. The wrapper checks policy access on every start/restart; the raw service checks the actual mark again before effects can fall back to all clients. Keep other policy/configuration writers idle during activation.

The browser UI defaults to HTTP on a concrete private LAN IPv4/loopback and warns that credentials and session cookies are unencrypted. A unique active private bridge address may be offered; ambiguous/WAN/tunnel interfaces are not auto-selected. Controller upstream remains verified loopback HTTPS. Prepared HTTPS UI remains supported. Stable signed update checks default on, with `auto_apply: false` always required.

## Transaction and recovery contract

Per-dependency journals precede payload/link publication, use random attempt tokens and independent payload identities, and serialize approval/recovery with `flock`. Exact no-overwrite publication refuses directory/symlink races. `dependency-provision.sh xray|xkeen --recover` finalizes an already complete matching publication or rolls back matching partial content. Changed/unknown content is retained for manual inspection; old nonempty journals without independent payload identity cannot authorize deletion.

`native-bootstrap.sh /absolute/stage --approve` consumes staged `configs/*.json` and optional token-only `xkeen.json`, publishes a private native tree plus exact no-overwrite links, and never runs the service. Its private pending journal supports `--recover` without the original stage: complete unchanged publications finalize; inactive partial unchanged publications roll back. Activation/runtime edits invalidate destructive recovery. Native files already approved and installed are retained when the later application wizard/installation fails.

KRM static installation has its own private journal under `/opt/var/lib/kee-route-manager-install/pending-MODE`. It snapshots intended bytes/modes and records file identity before publication, including staged credentials and original directory permissions. `KRM_INSTALL_ACTION=recover` removes only unchanged owned static files **before launcher import/activation**, retaining unrelated files/directories. At the durable launcher or start boundary recovery refuses destructive rollback; `KRM_INSTALL_ACTION=resume` verifies recorded files and continues the matching signed bootstrap/service/readiness without rewriting credentials, config or controller state. Exact interrupted launcher publication links can resume only against the same verified committed bootstrap. Drift or ambiguous incomplete intent requires private reconciliation. See runbook commands and [limitations](KNOWN_LIMITATIONS.md).

## Remaining acceptance gate

Actual exact-model Keenetic/Netcraze installation, LAN traffic, UI login, reboot, abrupt power loss, native policy/interception and recovery are **unrun**. Container fixtures, genuine Xray offline validation, signed fixtures and cross-builds do not establish router hardware acceptance. RC publication is authorized after software acceptance with these limits visible. Stable promotion and hardware qualification remain separate decisions.
