# Known limitations

**Toolchain security:** version 2.0.4 builds with Go 1.27.3 and includes [GO-2026-6809](https://pkg.go.dev/vuln/GO-2026-6809) (`crypto/x509` compromised-intermediate distrust). The immutable legacy v1.3.3 release uses affected Go 1.27.2 and is not repaired by this source change. Only install the complete signature-verified v2.0.4 assets once actually published; never substitute unverified development builds. Signature validity is independent of known-vulnerability and hardware acceptance checks.

Only Keenetic/Netcraze are current router targets. Hardware compatibility remains experimental; Version 2.0.1 includes MIPS BE; native hardware verification remains pending and immutable v1.3.3 has no BE binary. See [hardware catalogue](HARDWARE.md) and [offline configuration migration](BREAKING_CHANGES.md#201-keeneticnetcraze-only-router-targets).

- Panel permissions apply to KRM API operations, not OS/root access or individual LAN-device ownership. Already accepted operations may finish after permission revocation. Downgrading uses the original single-account credentials and cannot preserve new users or revoked rights; back up both private credential files.
- Dashboard history is limited to 720 successful in-memory samples and is lost on daemon restart. Gaps remain gaps. Keenetic WAN traffic is aggregate interface traffic, not VPN-only traffic. Device metrics depend on available KeeneticOS/NDMS RCI capabilities. No new hardware acceptance is implied by the dashboard or concurrent-control implementation.

- Published v1.0.0-rc.2 has a confirmed Xray multi-file routing defect: later routing sections replace its balancer and API rules. Current source fixes the merge and has a real-Xray lifecycle regression, but published assets are immutable. A separately signed corrected build is required for deployment.

- All Keenetic/Netcraze models remain experimental; [the model catalogue](HARDWARE.md) separates software gates from hardware acceptance. One Keenetic router has passed signed launcher migration and a manual GitHub release update through the authenticated panel API, preserving the Xray process, active node, device policy, credentials and TLS certificates. Router VPN health checks passed; one selected LAN client was confirmed working on the preceding private build. Reboot, power-loss, deliberately broken candidate rollback and exhaustive LAN-client acceptance remain separate hardware checks.
- Keenetic independent platform direct bypass is unsupported; a dead Xray does not automatically become working direct there. Existing unmanaged interception on any platform cannot be safely bypassed by KRM.
- Keenetic client policy changes use separate RCI reads and writes, without an atomic conditional save; external configuration writers must remain idle during the operation. After cancellation or a lost save response, KRM restores the running host policy and waits within the recovery deadline for the preceding asynchronous save before persisting the rollback. If that save cannot be confirmed, KRM reports an incomplete rollback; startup configuration requires operator reconciliation and may still contain the canceled policy. These recovery timings remain unverified on hardware.
- Existing interception and IPv6 policy remain operator-owned. No independent bypass or IPv6 leak-protection claim.
- Protocol1 updates require the separately installed stable launcher. Failed or interrupted read-only trials roll back; after the durable activation decision, crashes restart the committed version without restoring old state. The launcher itself, service scripts and config schema migrations require separate maintenance. Separate remote management UI is updated independently. Router power-loss and deliberately broken candidate hardware tests are not claimed.
- Only Xray is implemented. AmneziaWG and other VPN backends are not shipped; the abandoned draft PR #26 was never merged. Nodes: supported VLESS URI formats and bounded Xray JSON extraction for Reality TCP / WebSocket TLS; no sing-box adapter, arbitrary provider JSON schema, custom routing, outbound chains or general JSON passthrough. Device-bound providers require a stable configured HWID and a free device slot; live provider acceptance remains separate from syntax tests.
- WAN-vs-VPN evidence depends on direct probes actually traversing WAN on the target installation; targets sharing a hostname cannot meet independent quorum. Network/DNS ambiguity preserves selection rather than guessing.
- A benchmark hot-pool refresh can require restarting Xray depending on its dynamic API capabilities; existing connections may be interrupted. Failed remote connections cannot migrate.
- Startup reconciliation uses durable intent and actual runtime/file/firewall checks; exhaustive real kill-9/power-loss/kernel behavior awaits hardware qualification. Do not treat fake step replay as a real router crash test.
- Restore preserves unrelated edits and fails on irreconcilable owned-rule drift. A private backup and recovery path remain necessary.
- Installer is a clean-install flow using either prepared private config or the signed RU/EN wizard; it refuses overwrite. Configless core/local-ui require an interactive terminal; local-ui generates both controller and UI configs with HTTPS upstream and controller certificate trust. Standalone remote UI still requires prepared UI config, trusted upstream CA and an authenticated SSH tunnel. These installer changes require a new signed release; published assets are unchanged. It installs KRM only, not Entware/XKeen/Xray or an SSH tunnel service.
- Remote UI requires trusted CA/SPKI and an authenticated tunnel or verified proxy because core API stays loopback. A successful local Keenetic UI check does not qualify other router models or firmware; all catalogue models require individual acceptance.
- Panel RC/Release channel switching requires a compatible separately maintained launcher and enabled GitHub discovery. Manual signed manifest URLs retain their configured channel. Switching cannot update the stable launcher itself or make a lower SemVer eligible; `1.1.0-rc.13 → 1.0.0` is a downgrade. A discovery preference never invalidates an installed signed slot.
- GitHub update discovery scans the 100 most recent releases; repositories with longer active release histories may need explicit manifest URLs. Application requires a compatible launcher and explicit user action.
- SPDX inventory describes shipped files and project license/toolchain version; it is not a complete file-level transitive Go standard-library SBOM.

Xray loopback TCP API is unauthenticated by Xray design. Process locks serialize KRM owners, but do not prevent another local process calling Xray directly. On any multiuser Entware or management host, local users must be trusted or the administrator must restrict that API port by OS/firewall policy; do not expose it off-host. KRM socket permissions do not authenticate Xray gRPC.

Pending legacy journals without per-file replay identities cannot safely authorize ambiguous interrupted writes. Detected drift, or a missing baseline identity on a persistent backend, requires operator reconciliation; KRM retains the journal and edited files. New journals allow only the recorded before/after identity of each owned file, including partially applied writes. Unrelated routing edits made after intent was recorded are preserved by refusing replay until reviewed. Regular-file subscription cancellation cannot interrupt a kernel-blocked filesystem operation (for example a stalled network filesystem).

- Runtime settings reload cancels/joins a current test, resets in-memory metric history and starts scheduler timers anew, retaining the configured intervals and suppressing an extra startup benchmark. Pool-size, target/infrastructure and externally changed YAML require explicit maintenance outside this editor.
- Panel address editing requires a compatible separately maintained launcher and locally supervised UI; separate remote UI does not expose it. It changes hostname/port, not the bind IP. New hostnames use separate self-signed SNI certificates, require client trust and may require login; up to sixteen additional active UI hostname identities are supported. Existing aliases are retained on rollback. Device power-loss acceptance is still unrun; automated journal tests do not replace it.
- Keenetic local DNS save shares the NDMS global-configuration constraint: whole-file ownership/checksum checks refuse observed unrelated writes, but NDMS has no atomic conditional save. Writes tolerate delayed checksum publication and verify full saved commands; an unresolved DNS journal keeps the API available for retry and blocks client-policy saves. Keep external/native configuration writers idle during a DNS addition. A writer racing after the last check can still cause an unconfirmed save; recovery refuses observed drift instead of overwriting it. No other OS/router deployment is supported.

- Some Keenetic firmware denies loopback `/ci/` configuration export. Version1.2.1+ falls back to validated local `ndmc more running-config` / `more startup-config` reads after HTTP403/404. Missing or malformed exports remain a refusal; native checksum and whole-configuration guards still apply. Version1.2.0 may refuse hostname-based panel application on such firmware; its immutable assets are not replaced.

- Stable node exclusions require a constant configured source ID and parsed node name; names are case-sensitive. Renaming or recreating a source ID starts a new preference. Entries without names use endpoint labels and cannot follow endpoint rotation. Duplicate names within one source share the setting. Old multi-source caches do not retain every original name: ambiguous/missing legacy attribution stays fingerprint-bound until recovered, and a node already rotated beyond that cache may need to be excluded once again. Partially recovered legacy source attribution is persisted across cache replacement/restart. Explicit re-enable records take precedence for their known identities. If a refresh attaches an excluded alias to the active connection, it is refused without replacing that routing cache; resolve by switching nodes or enabling the alias. Older 2.0.2 / 2.1.0-rc.3 binaries do not understand logical preferences; manual downgrade can discard them and old strict trial readers reject the additional state/cache fields. No new router hardware acceptance is implied.
